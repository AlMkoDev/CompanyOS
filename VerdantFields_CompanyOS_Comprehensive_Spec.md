# **PART 1 — PLATFORM OVERVIEW: CompanyOS**

CompanyOS is a Virtual Company Operating System (VCOS) designed to digitally replicate, govern, and optimize the internal workings of Verdant Fields AgriTech Ltd. Unlike traditional ERPs or project management tools that focus on output, CompanyOS focuses on architectural integrity — serving as the single source of truth for "How this company works."

# **PART 3 — OPERATIONAL GAP ANALYSIS**

The Gap Analysis identifies the three specific gap types that exist between the written specification and a genuinely operational company. All three must be closed in sequence: Data first, then Technology, then Process.

| Gap Type | Core Problem | What Closes It |
| :---- | :---- | :---- |
| PROCESS GAP | Workflows documented in the spec are not yet adopted, consistently followed, or enforced in daily work across any department. | SOP creation, structured staff training, manager accountability mechanisms, and formal SOP governance. |
| TECHNOLOGY GAP | Systems listed in each department's data pack either do not exist, are not configured for the spec's workflows, or are not integrated with adjacent systems. | Technology audit, systems selection, configuration to match spec workflows, and end-to-end integration. |
| DATA GAP | Data assets identified in the spec exist in some form but are incomplete, inaccurate, inconsistently defined, or inaccessible to the people and systems that depend on them. | Data governance framework, systematic data cleaning, master data standards, and automated data pipelines. |

## **3.2  SOP Requirements — What Every SOP Must Contain**

| SOP Component | Required Content | Why Non-Negotiable |
| :---- | :---- | :---- |
| Title, Version & Dates | Document title, version (v1.0), effective date, next mandatory review date (max 12 months) | Enables version control; ensures the SOP does not become stale without detection |
| Purpose Statement | What outcome does this process produce, and why does the business need it to be consistent? | Grounds the SOP user in the intent of the process, not just the mechanics |
| Scope | Which roles, cost centres, transaction types, and geographies this SOP applies to | Prevents misapplication to situations the SOP was not designed for |
| Trigger / Input | The specific event, date, request, threshold, or system state that starts this process | Without a defined trigger, the process starts inconsistently — or not at all |
| RACI Per Step | Responsible (does it), Accountable (owns outcome), Consulted (must be asked), Informed (must be notified) | Eliminates the most common process failure: ambiguity about who owns each step |
| Step-by-Step Procedure | Numbered steps. Each step: action verb \+ role \+ system used \+ decision point \+ exception path | Removes interpretation. Followable with zero tribal knowledge |
| Approval & Escalation Matrix | At what value, risk level, or exception condition does this require escalation? To whom? Via what channel? | Ensures the authority matrix is embedded in the process, not bypassed |
| Output / Completion Standard | How does the performer know it is complete? What does the output look like? Where is it stored or sent? | Prevents partial completions being treated as done |
| Systems & Templates Used | Every system accessed, every template completed, every report produced during this process | Makes the SOP executable without knowing where things are |
| Exception Handling | The three most common things that go wrong, and the defined response to each | Prevents every exception escalating to a manager unnecessarily |
| Related Documents | Links to policy, authority matrix, system user guides, other SOPs this one depends on | Connects the SOP to the broader governance framework |

## **6.1  Technology Stack Recommendations**

| Component | Recommended Technology | Rationale |

| Monitoring | Prometheus \+ Grafana (open source) | No per-host fees; full observability stack self-hosted |
| Log Aggregation | Loki \+ Grafana (open source) | Part of Grafana LGTM stack; no Splunk subscription required |
| Infrastructure | Docker Compose (dev) → Kubernetes (prod v2) | Start simple, scale without vendor lock-in |
| Feature Flags | Unleash (open source) or Flagsmith | Incremental rollouts, A/B testing, no SaaS cost |

## **6.2  Architecture Principles**

| Principle | Rule | Implementation |
| :---- | :---- | :---- |
| API-First Design | Every module exposes a documented REST API. No direct DB reads between modules. | OpenAPI/Swagger auto-generated. All cross-module data access via API contracts. |
| Multi-Tenancy | All data partitioned by organisation\_id. No data leakage across tenants. | Row-level security in PostgreSQL. organisation\_id on every table. Global tenant middleware. |
| Event-Driven Integration | Use internal event bus (Redis Streams or Kafka v2) for cross-module async events. | e.g., "employee.hired" triggers ITSM provisioning ticket and payroll record creation automatically. |
| Audit-by-Default | All write operations produce an audit log entry. No exceptions. | Global audit middleware intercepts all POST/PUT/PATCH/DELETE. Logs to separate audit\_log table. |
| Fail-Safe Defaults | Permission denied is the default. Access must be explicitly granted. | RBAC middleware applied globally. Every route protected unless explicitly marked public. |
| Configuration over Code | Business rules (tax rates, approval thresholds, SLA times) stored in DB, not code. | ConfigurationTable per module. Admin UI to update without deployment. |

# **CLOSING PRINCIPLES & GOVERNANCE**

## **The Three Non-Negotiable Sequencing Rules**

| Rule | Statement | Consequence of Violation |
| :---- | :---- | :---- |
| 1 — Data Before Technology | Clean and govern data assets before configuring the systems that depend on them. | Systems go live on dirty data. Reports are wrong. Trust in the platform is destroyed before it is earned. |
| 2 — Technology Before Process | Configure and test systems before writing SOPs that reference those systems. | SOPs become obsolete immediately. Staff trained on wrong process. Re-training cost \> original build cost. |
| 3 — Ownership Cannot Be Shared Equally | Every gap, every module, every data asset has one named owner — not a committee. | Accountability diffuses. Nothing moves. The specification remains a document, not an organisation. |
